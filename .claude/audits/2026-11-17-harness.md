## Trouvailles

### 1. Renuméroter une migration : la règle n'est qu'en mémoire
**Pilier** : contexte. **Preuve** : quand plusieurs branches prennent le même
numéro de migration, il faut renuméroter avant le merge et rendre la
migration rejouable, parce que la base des previews a déjà passé l'ancienne.
Seule la mémoire `migration-renumbering` le dit. Dans la fenêtre, le
coordinateur a dû le rappeler six fois (« re-fusionne main et renumérote ta
migration ») : #188 renumérotée 0014 → 0015 → 0016, et sa preview a échoué
avant qu'elle devienne rejouable ; #189 0016 → 0017 ; #191 → 0018 ; #204
renumérotée au merge ; avant, #161 et #164 (0013_discord). La copie de la
prod (#218) a buté sur une migration passée sous une ancienne date.
**Remède** : un paragraphe dans `CLAUDE.md` § Base de données ; après le
merge, la mémoire devient un renvoi.
**Impact attendu** : rappels « renumérote » du coordinateur et previews en
échec pour une migration rejouée — base 6 rappels et 1 preview du 2026-11-13
au 2026-11-16 — attendu 0 preview en échec — contrôle le 2026-11-24 —
sinon : un check CI qui rejoue chaque migration de la branche une seconde
fois sur la base de test.

### 2. Les noms de branche : la règle est hors du dépôt, et une session s'est crue limitée à une branche
**Pilier** : contexte. **Preuve** : le propriétaire veut des noms de branche
parlants (2026-11-13, mémoire `branch-names` et instructions du projet). Le
fil des captures a poussé #221, #231 et #235 sur `claude/project-thread-r0xmts`,
et a mis dans #231 un changement que le coordinateur voulait dans une PR à
part, en écrivant « je ne peux pousser que sur une branche » : la consigne de
session (« Develop on branch claude/project-thread-… ») l'a emporté, faute
d'une permission écrite dans le dépôt. Mises à part les cinq PR ouvertes
avant la consigne (#161, #164, #170, #186, #188), les 23 autres ont un nom
parlant.
**Remède** : une phrase dans `CLAUDE.md` § Ouvrir une pull request, qui donne
la permission d'avance : une branche par travail, nommée d'après lui, même si
la session en propose une autre.
**Impact attendu** : PR mergées sur une branche `claude/project-thread-…` —
base 3 sur 26 — attendu 0 — contrôle le 2026-11-24 — sinon : un check CI qui
refuse ce préfixe de branche.

### 3. L'adresse fixe des previews montre la preview d'une autre PR
**Pilier** : contexte. **Preuve** : dans le fil « Renommer l'app », la session
a donné `comptoirdeschasseurs-preview.vercel.app`, et le propriétaire a vu
l'ancien logo (« bah non là je vois "Registre de lomone" dans le logo »,
2026-11-13 23:17) : `preview.yml` y attache la dernière preview construite,
de n'importe quelle PR. Seule la mémoire `discord-login` le dit.
**Remède** : une phrase dans `CLAUDE.md` § Donner un lien pour essayer : le
lien d'une PR est celui de sa description ; l'adresse fixe ne sert qu'à
Discord, après avoir relancé la preview de la branche.
**Impact attendu** : liens de preview qui montrent une autre PR — base 1 —
attendu 0 — contrôle le 2026-11-24 — sinon : `preview.yml` cesse de déplacer
l'alias hors d'un déclenchement manuel.

### 4. La revue périodique est proposée à chaque merge, par chaque fil
**Pilier** : contraintes. **Preuve** : trois fils l'ont proposée sans réponse
avant le « oui » : « Téléverser le logo » (2026-11-16 15:27, 29 PR), « Trouver
les marchandises par leurs noms du jeu » (19:25, 29 PR), « Préremplir le nom
d'un article hors stock » (2026-11-17 07:24, 32 PR). Un fil ne sait pas qu'un
autre l'a déjà fait : la règle dit « après chaque merge ».
**Remède** : proposer, c'est ouvrir l'issue `harness` « Passe du harness
AAAA-MM-JJ » (celle que la passe utilise) ; si elle est ouverte, la
proposition est faite, on ne la répète pas.
**Impact attendu** : propositions répétées avant une réponse — base 3 —
attendu 1 — contrôle avec la prochaine passe — sinon : un workflow qui ouvre
l'issue au 20e merge.
